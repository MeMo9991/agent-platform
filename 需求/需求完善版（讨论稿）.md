# Agent 自动化中台需求（讨论稿 v2）

> 2026-11-03。基于《需求大纲（初版）》与后续讨论。本文只说明系统应提供什么能力、边界和验收结果；实现方式见《架构设计（讨论稿）》。

## 1. 目标与首期范围

系统从确定的工作入口接收 Bug 或开发任务，交给合适的 Agent 调查和处理，让人能持续查看进度、回答问题、审批风险、验收结果。一次任务应能贯穿事件接入、调查、开发、验证、审查、合并及发布；系统须保留可追溯的过程和证据。

首期服务一个团队、一个或少量受控仓库，代码仓库可按配置托管在 GitHub 或 GitLab；事件来源与仓库托管平台分别配置。系统支持定时扫描和 IM 主动推送两类事件入口，接入 Codex 与 Qoder。先以一个真实仓库和一条发布流水线完成闭环，再扩展来源和仓库。

首期不要求从闲聊中主动发现任务、跨项目自动合并相似问题、跨 Agent 迁移完整对话、自动生产发布、通用工作流编排或自动生成 Skill。

## 2. 事件获取与问题关联

1. 事件来源可配置启停、接收范围和扫描频率。重复推送或重扫同一条事件，不得重复建任务或重复触发外部动作；失败重试和服务重启不得漏掉事件。
2. 保留来源原始描述、图片附件引用、原帖链接和来源侧标识。源数据字段统一命名 `meta_data`。事件 ID 用于识别重投；来源 Bug ID、话题 ID 等用于查找相关任务，不能把不同来源中碰巧相同的数字当成同一 Bug。
3. 支持仅有中文描述和图片的 Bug。系统应读取图片里的可见信息，形成可核查的线索；无法读取图片或缺少仓库归属时，明确告知人需要补充什么。
4. 同一 Bug、同一话题或明确引用旧任务的新事件，应能关联历史任务。只因文字相似而被找出的任务作为候选交人确认，不能自动合并。
5. 已关闭任务的后续反馈仍能找到历史记录。相关问题优先利用原 Agent 会话调查；复用失败时明确提示并带入旧任务的关键事实。**复用会话不代表认定旧修复造成新故障，也不扩大旧任务的授权。**
6. 若原故障再次出现，可重开原任务；若证实旧修复引入新故障且仍在原范围内，也可重开。证据不足时只保留关联候选；独立问题或超范围要求新建关联任务并重新授权。

## 3. Agent 调度与执行

1. 新任务由系统确定仓库、Agent 和执行优先级；已有归属的后续消息送到对应任务。关联不明确时，应展示候选与理由供人判断。
2. 开发任务之间可以并行，但同一任务的代码修改不能互相冲突。并发上限可配置；达到上限时排队。人工回复应优先唤醒等待中的任务。
3. Agent 的开发会话支持持续接收后续消息。强关联的新故障优先续用旧会话调查；无法安全恢复时，使用新会话和交接摘要，明确展示实际使用的方式。
4. 每次运行记录 Agent、模型、状态、开始和结束时间及可取得的用量。预算或时长达到上限时暂停并展示已完成结果，不得无限运行；无法准确取得用量时如实标注。
5. Agent 在代码定位时给出候选文件及依据；只有取得复现、日志、调用链、失败测试或版本对比等证据，才把候选称为根因。信息不足时向人提出一个具体问题。

## 4. 开发过程中的人机交互

1. 看板是常规交互入口：Agent 提问、进度、证据、人的回答和审批都能在任务页面查看。人的回答应送达正确会话；忙碌或暂时失败时不得丢失或重复执行。
2. 问题应具体，说明需要人决定的事项和影响；可继续的已授权工作不因一个问题全部停止。
3. 开发者可以查看原生 CLI 会话。人工直接接管时，平台应避免与人工同时操作同一任务，并记录接管后的结果。
4. 人在 CLI 对话中说“同意”不能代替平台的授权和审批记录。

## 5. 验证、审查、合并和发布

1. 每项代码交付应展示真实执行的验证命令及输出。开发阶段先做与改动有关的简要验证；独立验证和审查针对确定的代码版本。无法做的验证须标明原因。
2. 审查关注需求是否解决、是否引入缺陷、安全和权限风险；发现阻断问题须修复，或由有权者明确接受。审查循环须有限，不能无限相互修改和复查。
3. 能否自动修改和交付由任务授权范围及风险决定，不单凭改动行数。不可逆数据操作、权限与密钥、重要接口、CI/发布配置和生产发布须有更严格的限制；普通源码删除或增加配置按实际影响判断。
4. 超出原任务范围的工作须申请新授权。需审批的动作在批准前不得执行；批准只对所展示的动作和代码版本有效，版本变化后重新检查。
5. 每个任务的代码改动与其他并发任务隔离。合并前重新检查目标分支和必需的 CI；冲突或检查失败不得合并。发布作为独立步骤，生产发布默认需要明确批准，并记录结果及回滚信息。

## 6. 人工维护的 Skill

开发、验证、审查、发布各阶段的 Skill 由人在代码仓库维护和评审。平台在调用对应 Agent 时加载该阶段 Skill，并能说明一次运行使用了哪一版本。首期不自动生成、改写或沉淀 Skill。

## 7. 看板与运维

看板优先显示待回答、待审批、失败和超预算任务；任务详情显示来源、关联理由、授权、运行会话、改动版本、验证证据、审查意见、审批、合并与发布历史。人可暂停、恢复、取消、重试、手动关联或拆分任务，以及查看原始材料。系统应显示来源、队列、Agent、回复和发布环节的健康状态，并能在重启后继续未完成工作。

## 8. 首期验收场景

1. 同一事件重复投递只记录和处理一次；扫描中断并恢复后不漏事件。
2. 同一 Bug 的新评论能关联旧任务；只有相似描述时展示候选，不自动合并。
3. 中文描述与截图能进入调查，Agent 给出代码候选及证据；证据不足时提出具体问题，不猜测根因后直接修改。
4. 两个独立任务并行且互不覆盖；并发满时排队；人的回复被准确送回对应会话。
5. 修复发布后收到强关联反馈，优先恢复原会话调查；调查前不要求证明旧修复有错。不能续聊时明确说明并交接上下文。
6. 开发、验证、审查展示真实证据；新提交使旧检查和批准失效；阻断项未处理时不能合并。
7. 越权或高风险动作在执行前停止并请求人处理；驳回后没有对应外部副作用。
8. 合并冲突、CI 失败和发布失败可追踪、可恢复；生产发布没有明确批准则不能开始。
9. 系统重启后未完成任务继续推进，不重复发送回复、合并或发布。
10. 同一系统中的仓库可分别配置为 GitHub 或 GitLab；代码查询、检查、合并与发布必须使用对应仓库的配置，配置缺失时不得误操作其他仓库。

## 9. 待业务方确定

首个仓库及其 GitHub/GitLab 托管配置、扫描位置及事件格式、IM 产品与推送方式、目标分支、必需 CI、发布流水线和环境、审批角色、预算上限、数据保留期限，以及 Codex/Qoder 的使用账号和版本。这些决定部署配置与验收数据，不改变以上需求边界。
